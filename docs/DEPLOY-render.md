# Deploying Marden on Render (while Railway's builds are paused)

Railway paused builds and deploys platform-wide on 2026-10-21 (status.railway.com: major outage). The same
Docker images run on Render; `render.yaml` at this repo's root creates all three services in one step. Neon,
R2, Clerk, email and the env-var meanings are unchanged: see `DEPLOY.md` sections 1–6 and its variable tables.
Only the hosting steps below differ.

Cost (October 2026 list prices): `core-api` and `core-web` on Starter ($7/month each), `core-worker` on
Standard ($25/month, 2 GB, because the EIA/ERCOT spreadsheets, PDFs and QuantLib runs need more than 512 MB).

## Steps

1. Render dashboard → **New → Blueprint** → connect GitHub and pick `marketsights/marden-backend`. Render
   reads `render.yaml` and shows three services: `core-api`, `core-worker` (this repo) and `core-web`
   (`marketsights/marden-front-end`). Give Render's GitHub app access to both repos.
2. Render asks for every `sync: false` value. Use the same values `DEPLOY.md` lists:
   - **core-api**: `DATABASE_URL` (Neon pooled, role `app_rw`), `DATABASE_URL_UNPOOLED` (Neon direct),
     `CLERK_SECRET_KEY`, `CLERK_PUBLISHABLE_KEY`, `CLERK_WEBHOOK_SIGNING_SECRET` (after step 5; leave empty
     first). `WEB_ORIGIN` is set to `https://app.marden.ai` in `render.yaml`.
   - **core-worker**: the two database URLs, `ANTHROPIC_API_KEY`, `FRED_API_KEY`, the three ERCOT values,
     `RESEND_API_KEY` (or add `POSTMARK_TOKEN` by hand), `ALERT_FROM_EMAIL`, and the three `R2_*` values.
     `MARDEN_APP_URL` is set to `https://app.marden.ai` in `render.yaml`. `ALERT_LINK_SECRET` is generated by Render on core-worker and copied to core-api
     (`fromService`), which verifies the unsubscribe links with it.
   - **core-web**: `API_ORIGIN` = core-api's public URL (`https://core-api….onrender.com`, or
     `https://api.marden.ai` once the domain is set), `NEXT_PUBLIC_CLERK_PUBLISHABLE_KEY`, `CLERK_SECRET_KEY`.
     `API_ORIGIN` is baked into the build, so changing it needs a manual redeploy of core-web.
3. **Apply**. Each backend service runs `marden-migrate` before it starts (dbmate with an advisory lock, so the
   two pre-deploys never collide). Watch `core-api` → Logs until `/healthz` answers 200.
4. **Seed and first runs**: Render Shell on `core-worker` (or a one-off job) runs the commands in `DEPLOY.md`
   section 7 (`python -m marden seed all` needs the seed archive: upload it to R2 or run the seed from a
   machine that has it, with the worker's two database URLs), then the collectors, models and read models in
   the order given there.
5. **Domain (required before anyone can sign in)**: the Clerk production instance is on `marden.ai`
   (its Frontend API is `clerk.marden.ai`), and Clerk production keys only work on that domain and its
   subdomains, so the web app must be served at `app.marden.ai`, not at its `onrender.com` URL.
   core-web → Settings → Custom Domains → add `app.marden.ai`; at your DNS host add the CNAME Render shows
   (`app` → `core-web-….onrender.com`); wait for Render to verify it and issue the certificate. The API can
   stay on its `onrender.com` URL: browsers only call `app.marden.ai/api/*`, which the web app forwards to
   `API_ORIGIN`. (Optional later: `api.marden.ai` for core-api, then update `API_ORIGIN` and redeploy core-web.)
6. **Clerk**: in the Clerk dashboard (the marden.ai production instance) confirm `app.marden.ai` is allowed
   (a subdomain of the instance's domain; add it under allowed origins / redirect URLs if Clerk lists them),
   and add the webhook endpoint `https://<core-api URL>/api/webhooks/clerk` (events: organization,
   organizationMembership, organizationInvitation, user); paste its signing secret into core-api's
   `CLERK_WEBHOOK_SIGNING_SECRET` and redeploy core-api.
7. **Smoke test**: `scripts/smoke.sh --api https://<core-api URL> --web https://app.marden.ai` (add
   `SMOKE_TOKEN='<token>'` for the signed-in checks; `DEPLOY.md` section 7, step 9).

## What changes compared with Railway

- Dev sign-in is refused on Render as on Railway: the API, worker and web treat `RENDER` /
  `RENDER_SERVICE_ID` as deploy markers (besides `NODE_ENV=production`, which the images set).
- `/healthz` reports Render's `RENDER_GIT_COMMIT` as the running commit.
- Render's proxy is one hop, so `TRUST_PROXY=1` stays right.
- Render routes the public URL to the port in `PORT` (it sets 10000); both web services read `PORT`.
- Shutdown: Render waits `maxShutdownDelaySeconds` after SIGTERM before it kills a process (default 30 s).
  `render.yaml` gives core-worker 120 s, as Railway's `drainingSeconds`, because the worker gives running
  jobs 90 s (`MARDEN_WORKER_SHUTDOWN_TIMEOUT`); the API drains in 20 s and the web in less, inside the
  default. `services/tests/test_render_blueprint.py` checks this and the worker's variables.
- Branch: the services build `claude/modest-bardeen-tkbmaq` until it is merged; then set all three to `main`
  (in `render.yaml` and the dashboard).
- When Railway is back, `railway.json` files still work; run one host at a time against the same Neon
  database (both would run the worker's schedules otherwise).
